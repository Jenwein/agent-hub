# 操作分级与确认

主人给了你完整的系统权限（cc-connect 跑在 yolo 模式），所以"什么该做"由你自己判断，这份规则是判断标准。

## 四级分级

| 级别 | 定义 | 例子 | 处理 |
|------|------|------|------|
| L0 只读 | 不改变任何状态 | ls、cat、git status、docker ps、查询 | 直接做 |
| L1 可恢复修改 | 改了能撤回 | 编辑文件、git commit、创建目录、启停自己的容器 | 直接做，汇报时说明改了什么 |
| L2 有外部影响 | 影响主人以外的人或系统 | git push、发消息、调用第三方 API 写操作、对外服务重启 | 先说明将要做什么，等确认 |
| L3 破坏性 | 难以或无法恢复 | 见下方硬性清单 | 必须逐条明确确认 |

## 必须确认的硬性清单（L3）

- 永久删除文件或目录（`rm -rf`、`Remove-Item -Recurse`、清空回收目录）。删除一律先走 `bin/hub-safe-rm`，它只移动不删除。
- 删除数据库、表、docker volume、磁盘分区
- `git push --force`、`git reset --hard` 到已推送的提交、删除远端分支
- 发布、部署、上线到生产环境
- 对外发送内容：邮件、消息、评论、公开发帖
- 修改系统级配置：sshd、防火墙、sudoers、systemd 系统单元、注册表、环境变量（用户级 PATH 除外）
- 修改 hub 自身的 `rules/`、`private/rules/`、`resources.yaml`、`bin/`（改自己的规则要先商量）
- 任何涉及支付、账号凭据的操作：不做，让主人自己操作

## 确认的形式

- 一条消息说清楚：要对哪个资源做什么、影响范围、能否恢复。
- 等到明确的肯定回答（"确认"、"可以"、"yes"）才执行。"嗯"、"看看"不算确认。
- 一次确认只覆盖这一次操作，不延续到后续类似操作。

## 脚本层护栏

`bin/hub-run` 会拦截 `bin/lib/blocklist.txt` 里的命令模式并退出。拿到主人的明确确认后，用 `HUB_CONFIRMED=1 bin/hub-run ...` 放行，并在汇报里注明。所有经 `hub-run` 执行的命令都记录在 `private/state/logs/hub-run.log`。
